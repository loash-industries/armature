# Changelog

## 2026-09-26 — threshold and permission floors enforced inside dao (ARMATURE-24, ROAD-39)

- `dao::enable_proposal_type`, `dao::update_proposal_config` and creation-time overrides now run `assert_config_floors` on every config they store, so a caller holding a request can no longer skip the floors that used to live only in `admin_ops`: the type's own floor (`min_approval_threshold_for_type`: 66% EnableProposalType, 80% UpdateProposalConfig / EnableBypassType) and the new permission floor, `dao::permission_floor(bits)`, which is 80% if the config holds TYPE_ADMIN, MIGRATE, TREASURY_WITHDRAW or VAULT_EXTRACT. Both abort with `EThresholdBelowMinimum`. `admin_ops::assert_threshold_meets_floor` and `EThresholdBelowFloor` (5) are removed; the two tests that expected it now expect `dao::EThresholdBelowMinimum`.
- Grant rules (`assert_may_change_permissions`), checked whenever a config change alters a type's bits: the request must be EnableProposalType, EnableBypassType or UpdateProposalConfig (`EPermissionChangeNotAllowed`, 19), must not target its own type (`ESelfPermissionChange`, 20), and the floor of the bits added must not exceed the granting meta-type's own floor (`EGrantFloorNotMet`, 21), so the granting vote is held to at least the power granted. EnableProposalType (66%) therefore grants only low bits; high bits come from UpdateProposalConfig or EnableBypassType (80%). Removing bits follows the same requester rules with no floor. Privileged controller requests skip the grant rules but not the floors. `CompositePayload` can never hold bits (`ECompositeHoldsPermissions`, 22).
- `UpdateProposalConfig` gains `permissions: Option<u64>` (set with `with_permissions(bits)`, read with `permissions()`; `new` is unchanged) and `admin_ops::execute_update_proposal_config` applies it.
- Composite grants are standalone-only. `composite::add_step<P>` aborts with `EUseTypedStep` (16) for EnableProposalType and UpdateProposalConfig; use `add_enable_proposal_type_step` (aborts `EGrantInComposite` (17) if the new config has bits) or `add_update_proposal_config_step` (aborts if the payload changes the target's bits, `ETargetNotEnabled` (18) if its key resolves to nothing). Client PTB builders for composites that include these steps must switch to the typed entry points.
- Tests: framework 321 → 340, proposals 120.

## 2026-09-26 — per-type permission bits and dao::assert_permitted (ARMATURE-22, ARMATURE-23, ROAD-39)

- New module `armature::permissions` defines the bits a proposal type may hold: `board_add`, `board_remove`, `board_set`, `type_admin`, `pause`, `migrate`, `metadata`, `treasury_withdraw`, `vault_store`, `vault_borrow`, `vault_extract` (bits 0–10), plus `all()`, `contains(mask, bits)` and `assert_valid(mask)` (`EUnknownPermission` for undefined bits).
- `proposal::ProposalConfig` gains `permissions: u64`, deny-by-default like `composable_allowed`: `new_config` keeps its signature and sets 0; `with_permissions(bits)` replaces the mask (rejecting undefined bits), `permissions()` and `has_permission(bits)` read it. `TypeSlotAdded` / `TypeSlotConfigUpdated` carry the whole config, so the bits reach the indexer with no event change. `admin_ops::execute_update_proposal_config` and creation-time overrides of default types keep the slot's existing bits; no path can change bits yet (ARMATURE-24).
- `proposal::ExecutionRequest` gains `privileged: bool` (read with `req_is_privileged`). `proposal::privileged_execute` takes it explicitly: `controller::privileged_submit` passes true, `external_execution::ticket_from_cap` passes false, so bypass requests are held to their type's bits. Vote, single-PTB and composite requests are unprivileged.
- `dao::assert_permitted<P>(bits, req)`: aborts `EDAOIdMismatch` for another DAO's request; passes a privileged request; otherwise aborts `ETypeNotEnabled` if `P` has no slot and `EPermissionDenied` (18) if its config lacks any of `bits`. `dao::is_permitted` is the non-aborting form. No mutator calls it yet (ARMATURE-26–29). Test helper `proposal::new_privileged_request_for_testing`.
- Tests: framework 310 → 321 (`permissions_tests`), proposals 119 → 120 (UpdateProposalConfig preserves bits).

## 2026-09-26 — MintAllowance bypass is open minting: confirmed (ARMATURE-21, ROAD-39)

- New test `currency_ops_tests::mint_allowance_bypass_open_to_non_member` proves the hole: after a board passes `EnableBypassType<MintAllowance<T>>`, a non-member borrows the `ExternalExecutionCap` from the shared vault (`capability_vault::borrow_external_cap` is public), builds its own payload (`mint_allowance::new` is public), mints a ticket through `external_execution::ticket_from_cap` (no sender check) and receives the coins via `currency_ops::execute_mint_allowance`. Nothing identifies the "approved actor" the module docs describe. The test pins today's behaviour; the bypass-cap task (ARMATURE-31) will turn it into an expected failure.
- Testnet check: neither deployed framework package (`0xb363…4880`, `0xee0b…c048`) has emitted `BypassEnabled` or `ExternalExecutionCreated`, so no live DAO holds a MintAllowance bypass cap and nothing needs disabling. Tests: proposals 118 → 119.

## 2026-09-26 — emergency freeze keyed by Move type (ARMATURE-15)

- `emergency::EmergencyFreeze.frozen_types` and `freeze_exempt_types` are now keyed by the payload's canonical `TypeName` (`with_defining_ids`), the same key as the DAO's type slots, so freezing `PlaceLimitOrder<CRED>` blocks only that instantiation. The API is generic: `freeze_type<P>(cap, clock)`, `unfreeze_type<P>(cap)`, `is_frozen<P>(clock)` and `assert_not_frozen<P>(clock)`, plus `is_frozen_by_name`, `is_exempt_by_name` and `is_mandatory_exempt`. `governance_unfreeze_type`, `add_freeze_exempt_type` and `remove_freeze_exempt_type` take a `TypeName`. The mandatory exempt types are resolved from the framework's `TransferFreezeAdmin` and `UnfreezeProposalType` structs rather than name strings, so a same-named type in another package gets no exemption.
- The atomic, bypass, composite and two-PTB paths all call `assert_not_frozen<P>`. The two-PTB path used to check the display key recorded at submission, which let a pending proposal avoid a freeze if its type was disabled and re-enabled under a new key; that gap is closed.
- Payloads: `UnfreezeProposalType::new<T>()` (field `type_name`), and `UpdateFreezeExemptTypes::new()` followed by `add_type<T>()` / `remove_type<T>()`. `TypeFrozen`, `TypeUnfrozen`, `FreezeExemptTypeAdded` and `FreezeExemptTypeRemoved` carry `type_name` (the full type string, as `TypeSlotAdded` does) instead of `type_key`. Client PTB builders and the indexer must follow (ARMATURE-16); specs still describe string keys (ARMATURE-17). Tests: framework 303 → 310, proposals 118, world bridge 19.
- Added `packages/armature_external_type_tests`, a test-only fixture package (never published) that plays a third-party integrator. It defines its own generic payload `Rebalance<phantom T>` and handler, enables it by board vote through the production handlers (`admin_ops::execute_enable_proposal_type`, `external_execution::execute_enable_bypass_type`), and executes it on the read-only two-PTB, atomic and bypass paths. It also checks that `freeze_type<Rebalance<CredA>>` blocks all three paths while `Rebalance<CredB>` still runs, and that an `UnfreezeProposalType::new<Rebalance<CredA>>()` vote restores execution. 6 tests; CI's `packages/*` loop picks the package up.

## 2026-09-26 — table-backed board roster and snapshot-by-version voting (ARMATURE-13, ARMATURE-14)

- `governance::GovernanceConfig` is now a struct holding `members: Table<address, Member>`, `member_count` and `roster_version`, so the DAO root no longer grows with the board (test: adding and removing 100 members leaves the root's BCS size unchanged). Board is the only governance model: the unused `Direct` / `Weighted` variants, `InitDirect` / `InitWeighted`, `board_member_vec`, `board_vote_snapshot`, `board_members` and `ENotBoardGovernance` are removed. `roster_version` increments once per membership change, a batch counting as one. Each `Member` keeps its join/leave history as `Tenure`s, and a former member's entry is kept (closed) so eligibility at a past version stays verifiable; re-adding opens a new tenure. `is_board_member` means an open tenure, and execution and the Seal checks use it, so removed members lose both. Added `was_member_at`, `member_count`, `roster_version`, `member_vote_weight` and `init_members`. Destroying a DAO drops the roster table without reclaiming its entries' deposits.
- `Proposal.vote_snapshot` (a copy of the roster) is replaced by `snapshot_version`. A voter must have been a member at that version: members added later cannot vote, and members removed later still can. Quorum still uses the total weight at creation. The public vote entry point is now `board_voting::vote(proposal, &DAO, approve, clock)`, which aborts with `EDAOIdMismatch` unless the DAO is the proposal's own; `proposal::vote` became the package-internal `record_vote`. Client PTB builders must switch to the new entry point and pass the DAO (ARMATURE-16).
- `SetBoard` is now a diff, `{ to_add, to_remove }`, because a Table cannot be enumerated on-chain. `governance::set_board` / `dao::set_board_governance` apply it as one roster change, abort with `ENoBoardChange` (3) when both lists are empty, and rotate `encrypt_epoch` only when `to_remove` is non-empty. `board_ops::BoardUpdated` carries `added` and `removed` instead of `new_members`. Tests: framework 291 → 298, proposals 118.

## 2026-09-26 — PR #165 review fix: no votes after the voting period (ARMATURE-12)

- `proposal::vote` now aborts with `EVotingClosed` (20) once an Active proposal's voting period (`created_at + expiry_ms`) has ended. Before this, a late vote could still move an expired Active proposal to Passed and open a fresh execution window from `passed_at`, provided nobody had called `delete_expired_proposal` first. The deadline is computed by a new private `voting_deadline_ms` helper, which `delete_expired_proposal` also uses, so voting closes exactly when deletion opens. Code 18 (the removed `EPayloadNotConsumed`) is left unused so that abort codes from the old deployment still decode unambiguously. Tests: framework 289 → 291.

## 2026-09-25 — PR #165 review fix: saturating proposal deadlines (ARMATURE-12)

- Added `utils::saturating_add`, which returns `u64::MAX` instead of aborting on overflow. `proposal.move` uses it for the Active expiry deadline, the Passed execution deadline (`passed_at + execution_delay_ms + expiry_ms`), the execution-delay check and the cooldown check. `new_config` has no upper bound on `expiry_ms` or `execution_delay_ms`, so before this fix an enormous value overflowed and left a Passed proposal neither executable nor deletable. Such a config now means "never expires": the proposal stays executable, but `delete_expired_proposal` never opens for it, so it only leaves the chain by being executed. Accepted by design and documented on `new_config` and `delete_expired_proposal`. Tests: framework 286 → 289.

## 2026-09-25 — executed proposals are deleted, expired ones can be deleted by anyone (ARMATURE-12)

- `board_voting::ticket_from_vote` and `ticket_from_vote_readonly` take `Proposal<P>` by value. `proposal::execute` emits `ProposalExecuted`, moves the payload into the ticket and deletes the object, so the storage rebate goes to the executing transaction's gas payer (the gas station on sponsored flows). A second execute attempt fails because the object no longer exists. Client PTB builders pass the same shared-object argument; only the Move signature changed.
- `proposal::try_expire` is replaced by `delete_expired_proposal<P: store + drop>(proposal, clock)`, which anyone can call and which emits `ProposalExpired`. It deletes an Active proposal once `created_at + expiry_ms` has passed, and a Passed proposal once its execution window `passed_at + execution_delay_ms + expiry_ms` has closed. `execute` now aborts with `EExecutionWindowClosed` (19) after the window; before this change a passed proposal stayed executable forever and could never be cleaned up. Accepted behaviour: with the default 7-day expiry and 7-day freeze, freezing a type right after one of its proposals passes cancels that proposal.
- Removed `delete_executed_proposal`, the `Executed` and `Expired` status variants (`is_executed`, `is_expired`), `ENotExecuted` (14), `EPayloadNotConsumed` (18) and the `Option` around `Proposal.payload`. Off-chain readers must get the executed and expired statuses from `ProposalExecuted` / `ProposalExpired` (ARMATURE-16); specs and docs still describe `try_expire` (ARMATURE-17). Tests: framework 287 → 286, proposals 116 → 118, world bridge 19.

## 2026-09-25 — PR #164 review nits (ARMATURE-11)

- `proposal::privileged_create_for_testing` (test-only) no longer creates or shares a `Proposal<P>`: it mints the ID via `fresh_proposal_id` and drops its `clock` parameter, matching the production single-PTB paths. `CLAUDE.md` now describes single-PTB executions as event-only (no `Proposal` object) instead of an `active → executed` transition.

## 2026-09-24 — event-only audit for single-PTB executions (ARMATURE-11)

- `board_voting::submit_vote_execute` / `submit_vote_execute_readonly`, `external_execution::ticket_from_cap` / `ticket_from_cap_readonly` and `controller::privileged_submit` no longer create a shared `Proposal<P>` audit object. They mint the proposal ID from `ctx.fresh_object_address()` and emit the events a shared proposal would: `ProposalCreated`, `ProposalPayloadCreated`, then `VoteCast` and `ProposalPassed` on the vote path, and `ProposalExecuted`. A single-vote trade now creates zero framework objects; the officers OU had accumulated 743 undeleted audit objects (~5.35 SUI of locked deposits). The atomic path still returns a Standalone ticket with yes=1 and total=board size, so approval-floor checks and all abort codes are unchanged. Two-PTB `submit_proposal` still shares a `Proposal<P>`.
- `ProposalCreated` gains `metadata_ipfs: Option<String>` on every path, since no object carries it any more. The indexer's event struct must add the field (ARMATURE-16). `privileged_submit` now requires `P: store + drop` (the payload is serialised into `ProposalPayloadCreated`, which that path did not emit before, and then dropped) and no longer takes a `clock`. The five `subdao_ops` handlers that only forwarded it (`execute_pause_subdao_execution`, `execute_unpause_subdao_execution`, `execute_spin_out_subdao`, `execute_controller_batch_add_members`, `execute_controller_batch_remove_members`) drop their `clock` argument too, so client PTB builders must stop passing it (triex-app-api, signer-api allowlist; ARMATURE-16). On `ticket_from_cap`, `ProposalPayloadCreated` now precedes `ProposalExecuted`.
- Removed `proposal::create_returning`, `share_proposal`, `privileged_create`, `privileged_create_with_payload` and `emit_payload_created_event`; added `proposal::execute_single_vote`, `privileged_execute`, `ProposalConfig::passes` (pass rule now shared with `vote`), and `governance::board_vote_total_weight` and `board_vote_weight`. Board vote weight is defined once as `governance::BOARD_MEMBER_VOTE_WEIGHT` and read by the snapshot, the total and the atomic path; `board_vote_total_weight` aborts with `ENotBoardGovernance` (3) on non-Board governance. `testing/` is now git-ignored. Tests: framework 282 → 287.

## 2026-09-24 — read-only DAO on the atomic and bypass paths (ARMATURE-10)

- Added `board_voting::submit_vote_execute_readonly`, `board_voting::ticket_from_vote_readonly` and `external_execution::ticket_from_cap_readonly`. They take `&DAO` instead of `&mut DAO` and do not call `record_execution`, whose last-executed timestamp only feeds cooldown checks. They abort with `ECooldownRequiresMutableDAO` (`board_voting` 9, `external_execution` 14) when the type's `cooldown_ms > 0`; `ticket_from_vote_readonly` also rejects a proposal whose snapshotted config has a cooldown. A PTB that reaches the DAO only through read-only entry points can pass it as an immutable shared input, which is not versioned or rewritten and takes no write lock, so concurrent single-vote trades stop contending on the DAO. The `&mut` variants behave as before and now wrap shared `*_core` functions. Added `proposal::config` (snapshotted `ProposalConfig`). Composite pipelines still record every step (out of scope). Tests cover a cooldown raised on the slot after submission (snapshot has none) blocking `ticket_from_vote_readonly`, and `submit_vote_execute_readonly` aborting with `EInsufficientVotingWeight` when the caller's single vote does not meet quorum. Tests: framework 267 → 282.

## 2026-09-24 — enforce display key on default-type overrides

- Construction-time overrides (`apply_type_overrides`, reached via `create_tribe_configured` and the `create_*_configured` paths) now abort with `dao::EDisplayKeyMismatch` (17) when overriding a default-enabled type with a display key other than its seeded one. Previously the config was replaced but the override's key was silently dropped, so e.g. `new_type_init<UpdateMetadata>(b"UpdateMetadata", …)` left the key as "CharterUpdate" and later submissions naming "UpdateMetadata" aborted with `ETypeNotEnabled`. Documented two accepted behaviours: `disable_proposal_type` clears cooldown state, so a re-enabled type's first execution is not rate-limited; `ticket_from_vote` checks freezes against the submission-time display key rather than the slot's current key. Both require an EnableProposalType (66%) or EnableBypassType (80%) vote to exploit. Tests: framework 266 → 267.

## 2026-09-24 — type-keyed proposal registry (ARMATURE-9)

- Replaced the four string-keyed maps on `dao::DAO` (`proposal_configs`, `enabled_proposal_types`, `type_bindings`, `last_executed_at`) with one dynamic-field slot per enabled proposal type, keyed by the payload's canonical `TypeName` and holding its display key, `ProposalConfig` and last-executed timestamp; a second per-type field indexes display key → type for cold admin paths (config updates, disables, freezes by name) and enforces display-key uniqueness. The root object is now a few hundred bytes and does not grow with enabled types. Motivation: gas analysis of the testnet officers OU showed every transaction rewriting an 18.5 KB root, which was 88% of the non-refundable storage burn and roughly a third of computation; 23 of its 49 enabled types were stale entries from superseded trading packages that the old design could never prune.
- `board_voting::submit_proposal` / `submit_vote_execute`, `external_execution::ticket_from_cap` and `composite::add_step` no longer take a `type_key` argument: the payload type `P` selects the slot, so a payload cannot be submitted under another type's config and the binding map is unnecessary. `Proposal.type_key` and the proposal events keep carrying the human-readable display key.
- Moved the default and classification payload types (`SetBoard`, `AddMember`, `RemoveMember`, `BatchAddMembers`, `BatchRemoveMembers`, `UpdateMetadata`, `EnableProposalType`, `DisableProposalType`, `UpdateProposalConfig`, `TransferFreezeAdmin`, `UnfreezeProposalType`, `SpawnDAO`, `SpinOutSubDAO`, `CreateSubDAO`, `TransferAssets`) from `armature_proposals` into `armature_framework/sources/types/` so the framework can seed default slots and classify undisableable / SubDAO-blocked / migration-allowed types by `TypeName`; handlers stay in `armature_proposals`. `EnableBypassType`, `DisableBypassType` and `CompositePayload` moved into leaf modules for the same reason.
- `EnableProposalType` and `EnableBypassType` payloads now pin the Move type the board approved (`type_name`), and the handlers abort with `ETypeMismatch` if the executor's `NewType` differs — previously the executor chose the bound type at execution time. Construction-time config overrides (`create_tribe_configured`, `create_wired_subdao`, `create_*_configured`) take a `vector<ProposalTypeInit>` built with `dao::new_type_init<T>(display_key, config)`, which also closes the gap where override-enabled types never received a binding.
- New registry events `TypeSlotAdded`, `TypeSlotRemoved` and `TypeSlotConfigUpdated` carry the canonical type name, display key and config, and fire for default slots at creation as well as for governance changes. Tests: framework 258 → 266, proposals 115 → 116 (composite nesting test moved into the framework, where `CompositePayload` can be constructed), world bridge 19. Follow-ups: clients still pass `type_key` (ARMATURE-16), docs still describe string keys (ARMATURE-17).

## 2026-08-12 — automated whitepaper releases
