# Changelog

## 2026-09-24 — type-keyed proposal registry (ARMATURE-9)

- Replaced the four string-keyed maps on `dao::DAO` (`proposal_configs`, `enabled_proposal_types`, `type_bindings`, `last_executed_at`) with one dynamic-field slot per enabled proposal type, keyed by the payload's canonical `TypeName` and holding its display key, `ProposalConfig` and last-executed timestamp; a second per-type field indexes display key → type for cold admin paths (config updates, disables, freezes by name) and enforces display-key uniqueness. The root object is now a few hundred bytes and does not grow with enabled types. Motivation: gas analysis of the testnet officers OU showed every transaction rewriting an 18.5 KB root, which was 88% of the non-refundable storage burn and roughly a third of computation; 23 of its 49 enabled types were stale entries from superseded trading packages that the old design could never prune.
- `board_voting::submit_proposal` / `submit_vote_execute`, `external_execution::ticket_from_cap` and `composite::add_step` no longer take a `type_key` argument: the payload type `P` selects the slot, so a payload cannot be submitted under another type's config and the binding map is unnecessary. `Proposal.type_key` and the proposal events keep carrying the human-readable display key.
- Moved the default and classification payload types (`SetBoard`, `AddMember`, `RemoveMember`, `BatchAddMembers`, `BatchRemoveMembers`, `UpdateMetadata`, `EnableProposalType`, `DisableProposalType`, `UpdateProposalConfig`, `TransferFreezeAdmin`, `UnfreezeProposalType`, `SpawnDAO`, `SpinOutSubDAO`, `CreateSubDAO`, `TransferAssets`) from `armature_proposals` into `armature_framework/sources/types/` so the framework can seed default slots and classify undisableable / SubDAO-blocked / migration-allowed types by `TypeName`; handlers stay in `armature_proposals`. `EnableBypassType`, `DisableBypassType` and `CompositePayload` moved into leaf modules for the same reason.
- `EnableProposalType` and `EnableBypassType` payloads now pin the Move type the board approved (`type_name`), and the handlers abort with `ETypeMismatch` if the executor's `NewType` differs — previously the executor chose the bound type at execution time. Construction-time config overrides (`create_tribe_configured`, `create_wired_subdao`, `create_*_configured`) take a `vector<ProposalTypeInit>` built with `dao::new_type_init<T>(display_key, config)`, which also closes the gap where override-enabled types never received a binding.
- New registry events `TypeSlotAdded`, `TypeSlotRemoved` and `TypeSlotConfigUpdated` carry the canonical type name, display key and config, and fire for default slots at creation as well as for governance changes. Tests: framework 258 → 266, proposals 115 → 116 (composite nesting test moved into the framework, where `CompositePayload` can be constructed), world bridge 19. Follow-ups: clients still pass `type_key` (ARMATURE-16), docs still describe string keys (ARMATURE-17).

## 2026-08-12 — automated whitepaper releases

- Added `.github/workflows/whitepaper-release.yml`, triggered by pushing a `whitepaper/v*` tag: it verifies the tag against the document version, compiles the PDF with Typst, and publishes a GitHub release with `armature-whitepaper.pdf` attached. Made the version single-sourced as `#let version` in `whitepaper/main.typ` (rendered on the title page and greped by CI, so a mismatched tag fails the build). Release notes are hand-written per version in `whitepaper/releases/<version>.md` and reviewed in the PR that bumps the version, falling back to auto-generated notes if absent. Documented the process in `docs/whitepaper-release.md` and repointed the README whitepaper link from the pinned v0.1.0 tag to `releases/latest`.

## 2026-08-09 — whitepaper accuracy revision (v0.2)

- Corrected the whitepaper to align with the implemented Move framework. Clarified governance as Board-only with Direct/Weighted reserved as planned variants. Corrected voting to require both quorum and approval threshold. Stated safety-floor constants accurately (66% enable, 80% config-change/bypass). Fixed emergency freeze mechanics: `FreezeAdminCap` issued to creator, unfreeze/config/transfer require proposals, 7-day auto-expiry, unfreeze/transfer-admin permanently exempt. Documented composite proposals as fully implemented (≤16 steps, no nesting, component-wise max config). Reframed the Charter as a name + IPFS metadata-URI pointer, and the addressing/ticker-registry chapter and upward federation, as planned/unimplemented. Acknowledged the two governance-gated non-vote execution paths. Added missing built-in proposal domains (currency mint/burn, package upgrades).
