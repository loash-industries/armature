## Armature Project Whitepaper — v0.2.0

An accuracy revision. v0.1.0 described the intended design as though it were all
built; this revision separates what the framework does today from what is still
planned, and corrects the mechanisms that were described imprecisely.

### Implemented vs. planned

- Added a status note on the opening page: implemented features are described in
  the present tense, planned features are explicitly marked.
- **Governance models** — Board is the implemented style and every DAO created
  today is a Board DAO. Direct and Weighted are marked planned, held as reserved
  variants in a sealed, extensible enum.
- **Charter invariants** — marked planned. The chapter now describes the Charter
  as it exists (name plus a metadata URI) and frames on-chain invariants as the
  evolution rather than the current state.
- **Addressing scheme** — the whole chapter is marked planned. The Ticker
  Registry, recursive paths, and ticker capability do not exist yet; DAOs are
  referenced by object ID today.
- **Federation** — marked planned. The downward parent-child axis is built; the
  upward and sideways axes arrive with the federation layer.

### Corrected mechanisms

- **Charter storage** — corrected from "Walrus blob with an on-chain content
  hash" to what is actually implemented: a free-form metadata URI, by convention
  an IPFS reference. The integrity hash and explicit versioning are noted as
  planned.
- **Governance floors** — replaced vague wording ("near-unanimity",
  "supermajority") with the framework's actual constants: a 66% floor to enable a
  new proposal type, and an 80% floor to change a proposal type's own governance
  parameters or to enable the external-authorization bypass.
- **Vote passage** — clarified that quorum and approval threshold are two
  separate bars that must hold together, with votes weighted by snapshot.
- **Composite proposals** — documented the framework-enforced rules: a sixteen-step
  limit, no nesting, component-wise maximum of the steps' governance
  configurations, and cooldown types excluded unless explicitly marked composable.
- **Emergency freeze** — corrected the trust model. The `FreezeAdminCap` is issued
  to the DAO at creation and is transferable rather than vault-only; freezing is
  fast and unilateral while unfreezing is always a governance action. Documented
  the 7-day default expiry and the permanent freeze-exemption of the unfreeze and
  transfer-admin proposal types.
- **"No backdoors"** — qualified. All authority is rooted in governance, but two
  non-vote execution paths exist (a parent's override of a controlled Sub-DAO, and
  the opt-in external-authorization bypass), and both are themselves governed.
- **Sub-DAO control** — corrected from "replace its board" to add/remove board
  members, and documented that hierarchy-altering proposal types are
  framework-blocked for controlled DAOs.
- **Membership** — described the actual proposal types (`AddMember`,
  `RemoveMember`, batch variants, `SetBoard`) and the EVE Frontier world-bridge
  path for permissionless self-join against a tribe allowlist.
- **Built-in proposal types** — expanded the list to include currency issuance
  (minting and burning DAO-controlled coins) and package upgrades.

### Editorial

- Removed the open authoring questions left inline in the v0.1.0 draft.
- Clarified that composite execution runs through a hot-potato pipeline that must
  complete within a single transaction.
